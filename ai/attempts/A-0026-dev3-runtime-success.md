# A-0026 - Runtime-validate Phase 1 dev3 bounded staging/upload path

**Date:** 2026-08-20  
**Objective:** Prove on the reference Windows 11 / RX 6800 XT Vulkan system that Obsidian's custom bounded staging arena can persistently map host-visible upload memory, batch multiple copies into one submission, apply explicit backpressure instead of waiting/allocating, reclaim staging space only after GPU completion, and verify copied bytes deterministically.  
**Action:** User launched `Obsidian-0.1.0-phase1-dev3` with Minecraft 26.2, Fabric Loader 0.19.3, Fabric API 0.158.0+26.2, Java 25.0.1, and Vulkan. The one-shot upload probe staged two deterministic 128-byte payloads into the 262144-byte arena, encoded both copies into one command submission, deliberately requested an impossible full-capacity allocation while 256 bytes were occupied to force one backpressure event, then polled the batch fence nonblocking and read-mapped the destination for byte-for-byte verification. The user entered a single-player world and exited normally.  
**Result:** `SUCCESS`.  
**Intended effect:** Validate bounded persistent staging, batched copies, explicit admission failure under pressure, completion-gated ring reclamation, and data correctness without routine GPU waits or fallback upload allocations.  
**Actual effect:** On frame 1 Obsidian logged `copies=2`, `payloadBytes=256`, `stagingCapacity=262144`, `highWater=256`, `backpressureEvents=1`, `pendingBatches=1`. A later zero-timeout poll in the same frame iteration completed the batch and verified all copied bytes, logging `copiedBytes=256`, `reclaimedBytes=256`, `pendingBatches=0`, `backpressureEvents=1`. The player entered the world. Shutdown after 3037 frames reported `stagingSubmittedBytes=256`, `stagingReclaimedBytes=256`, `stagingHighWater=256`, `stagingBackpressureEvents=1`, `pendingUploadBatches=0`, `retiredResources=0`, `releasedResources=0`, `pendingRetirements=0`. Process exit code was 0.  
**Evidence:** User Prism Launcher log dated 2026-08-20 14:09-14:10 local time; Obsidian lines 251-259 show staging activation, batched submission, deliberate backpressure and successful readback verification; lines 293-307 show world entry/chunk rendering; lines 326-329 show clean accounting and exit code 0.  
**Why it worked:** Obsidian owns the staging ring's capacity/admission policy, uses Minecraft's low-level `GpuBuffer`/mapping/copy/fence abstractions, batches both copies into one encoder submission, and advances the reclaim cursor only after a real completion fence reports success. No fallback temporary staging allocation and no blocking reuse path was used.  
**Side effects / lessons:** Same-frame completion is valid because polling is zero-timeout. The deliberate backpressure event is expected and proves the failure path. Keep staging capacity bounded and expose pressure metrics when real terrain streaming arrives.  
**Next action:** Merge dev3 with `[no-release]`, then implement Phase 1 dev4 device-local geometry arena/suballocation with generation-safe handles, fragmentation/high-water metrics, completion-gated frees/reuse, and a deterministic allocate/upload/free/reuse/readback validation sequence.
